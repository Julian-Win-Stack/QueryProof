# QueryProof

A natural language interface to a real Postgres database, plus an eval harness
that measures how often it is right. Ask a question in English, it selects
relevant tables, an LLM writes SQL, it validates and executes read-only, and on a
Postgres error it feeds the error back and retries. The harness scores every
answer by running the generated SQL and the gold SQL and comparing returned rows.

The project exists to produce measured accuracy numbers. The README's results
table is the deliverable; everything else serves it.

## Stack

- TypeScript, Node. **No Python, ever.**
- `pg` for Postgres, `tsx` to run TypeScript directly
- `node:test` (Node built-in) for unit tests — no test-runner dependency
- `evalite` for eval run storage, repeat runs, and run-over-run comparison
- `openai` SDK, model **`gpt-5.6-terra`** — pinned. See below.
- Next.js for the demo frontend (phase 8, not built yet)

## Commands

```bash
npm run validate-gold          # executes all 500 gold queries -> gold/*.json
npm test                       # node:test — pure only, never touches Postgres
npm run test:db                # tests needing the container: role, catalog, executor
npm run lint                   # MUST pass before any commit
npm run smoke                  # one model call: parsed JSON, usage, rate-limit headers
npm run ask -- "<question>" [db_id]   # one question end to end; db_id scopes tables
npm run eval:dev               # frozen 100-question dev slice
npm run eval:easy              # all 500, tables scoped to the record's db_id
npm run eval:hard              # all 500, table selection on
npm run eval:pickers           # keyword vs LLM picker, one run, dev slice
```

The `eval:*` scripts do not exist yet — Phase 5 adds them.

Test files split by what they need, and the split is the filename: `src/*.test.ts`
is pure and runs under `npm test`, `src/*.dbtest.ts` needs the container and runs
only under `npm run test:db`. `.dbtest.ts` is deliberately not `.db.test.ts` —
`node --test` discovers anything ending `.test.ts`, so the second form would drag
Postgres into the pure suite.

**Every eval script is one eval file plus environment variables** (`MODE`,
`PICKER`, `REPAIR`, `DEV`, `CONCURRENCY`). evalite's CLI accepts no custom flags,
so `npm run eval:dev -- --picker=llm` silently does nothing. Never add a second
eval file to express a configuration.

## Where decisions live

- `CONTEXT.md` — the glossary. What a *run*, a *void run*, a *picker*, *table
  recall*, and *same rows* mean. Use these words; they are load-bearing.
- `docs/decisions.md` — **read before implementing any phase.** Every question
  `PLAN.md` left open, resolved, with reasoning and with what would invalidate
  it. Cited as **D1**–**D17** throughout the plan.
- `docs/adr/` — the two decisions with consequences big enough to need a page.
- `KNOWN_ISSUES.md` — deliberate divergences from BIRD's evaluation.
- `RUNS.md` — append-only log of every run, with its verdict.

The plan is executed across many sessions. A decision reversed without being
recorded produces two numbers that look comparable and are not.

## Structure

```
data/          BIRD Mini-Dev data + load.log        (gitignored, regenerated by script)
gold/          validated/rejected/quarantine.json   (gitignored, output of validate-gold)
scripts/       one-shot and measurement scripts
src/           library code
src/prompts/   one file per prompt version, each exporting PROMPT_VERSION
evals/         *.eval.ts, configuration comes from env, not from new files
evals/dev-slice.json  the frozen 100 ids — committed, never regenerated
runs/          one JSON export per eval run           (committed — this is the evidence)
CONTEXT.md     the project's glossary — what the words mean
docs/adr/      decisions that would otherwise look arbitrary
RUNS.md        append-only run log: approach, number, verdict
PLAN.md        phase-by-phase implementation plan   (gitignored, local only)
KNOWN_ISSUES.md  deliberate divergences from BIRD's evaluation
```

**Every run gets an entry in `RUNS.md`, and every entry gets a verdict** — `kept`,
`rejected`, or `void`. A `rejected` run is valid evidence whose approach lost; a
`void` run is not evidence at all (wrong config, crash, wrong model, cached
response) and its number is never compared to anything. Entries are never edited
after the fact.

Eval results live in evalite's SQLite store *and* in a committed JSON export per
run. Configure the store to a persistent path — evalite v1 defaults to
**in-memory**, so an unconfigured run keeps nothing at all.

## Environment

- `DATABASE_URL` — `postgresql://postgres:devpass@localhost:5433/bird`. Gold
  validation and the schema catalog. Never generated SQL.
- `DATABASE_URL_RO` — `postgresql://queryproof_ro:ro_devpass@localhost:5433/bird`.
  The only string generated SQL ever connects with. Create the role with
  `psql "$DATABASE_URL" -f scripts/create-ro-role.sql`.
- `OPENAI_API_KEY` — used directly by every eval run
- `RESPAN_API_KEY` — the gateway key, used *in place of* `OPENAI_API_KEY` on the
  product path only
- `MODEL` — overrides the pinned `gpt-5.6-terra`. Set it and every earlier number
  is retired, not carried forward.
- `EFFORT` — reasoning effort, default `medium`. **Not settled in
  `docs/decisions.md`** — pick a value before the Batch B runs, because it moves
  both cost and accuracy and every run records it.

All live in `.env` (gitignored). Read `DATABASE_URL` from env — never hardcode a
connection string, and **never hardcode a LAN IP**.

## Hard constraints

These bite on tasks that look unrelated to them.

**Postgres port 5433 is shared.** A native Postgres also binds `127.0.0.1:5433`
and shadows the Docker container `queryproof-pg`. The user stops it manually
before running anything. If a connection fails with `database "bird" does not
exist`, the native instance is answering — that is not a config bug.

**All 75 tables are in `public`.** Eleven BIRD databases merged into one
namespace, zero name collisions. There is no per-database separation in Postgres;
the only `db_id` → tables mapping is `data/minidev/MINIDEV/dev_tables.json`.

**Near-collisions are the real trap, not exact ones.** `races` is Formula 1
Grands Prix; `race` is alien species from the superhero database. Nothing in the
name says which database it came from. Table selection must survive this.

**Table names are lowercase in Postgres; column names are not.** `examination`
has `"Examination Date"`, `"aCL IgG"`, `"ANA Pattern"`. `dev_tables.json` holds
BIRD's *original* mixed-case names (`Player_Attributes`, `postHistory`, …) which
do **not** match Postgres. So: build every prompt and query from
`information_schema`, and quote every identifier exactly as stored. That one rule
removes all the special cases — including `order`, which is both a table name and
a reserved keyword and must always be written `"order"`.

One path exists — `loadSchema` / `renderSchema` in `src/schema.ts`. `renderSchema`
takes tables already chosen, so table selection stays in the caller. EASY mode's
`db_id` → tables lookup is `tablesForDbId`, which matches `dev_tables.json`
case-insensitively; 17 of its 75 names do not exist in Postgres as spelled.

**Gold record ids are array position, zero padded** (`bird-0000`). `question_id`
in the source file is **not** unique — ids 137 and 138 each appear twice.
**Never renumber.**

**Grading is execution-based only. No LLM judges anything, ever.** A query is
correct iff running it returns the same rows as the gold query.

**The row comparator's four rules.** Row order ignored. Column order
significant. Column names never consulted. Duplicates significant (multiset).
This is stricter than BIRD, which compares result *sets* and so forgives
duplicate rows — the exact symptom of a wrong join key, which is the most common
way an LLM gets SQL wrong. Deliberate divergence, recorded in `KNOWN_ISSUES.md`.
Never add a dedupe step.

**Value canonicalization happens up front, not on demand.** `pg` returns
`integer` as a number and `bigint`/`numeric` as a string, so two correct queries
using different aggregates compare unequal. Dates, nulls, and floats have the
same trap. Handle all four in the comparator from the start. This reverses an
earlier "leave it broken and measure each fix" recommendation — that call was
overruled and is settled.

**Rows arrive as arrays everywhere** (`rowMode: 'array'`). That is what makes
"column names are never consulted" structurally true rather than something the
comparison code has to remember.

**Gold records store no result fingerprint.** `validate-gold` records `rowCount`
and `columns` only. Value canonicalization lives in the row comparator and
nowhere else — do not add a second one, and never hash rows for comparison.

**Accuracy denominator is `|validated|`** — currently 500 (500 gold − 0
quarantined − 0 rejected). Read it from the file at runtime; a hardcoded
denominator produces a wrong percentage instead of an error.

**Every connection must `SET TimeZone = 'Asia/Shanghai'`.** The dump's
`timestamptz` literals all carry `+08`, so a naive timestamp literal in gold SQL
matches under no other zone — two gold queries return zero rows under UTC and
one row each under `+08`. Gold validation and eval execution must agree on this
or they are grading against two different clocks. Use the named zone: `'+08'`
is POSIX-style and means UTC−8. Reasoning in `KNOWN_ISSUES.md`.

**The dev slice is frozen.** `evals/dev-slice.json` holds 100 ids, stratified on
`db_id` × `difficulty`, generated once and committed. **Never regenerate it** —
a slice that moves makes every earlier run incomparable, silently. It lives in
`evals/` rather than `gold/` precisely because `gold/` is gitignored and an
uncommitted slice differs between machines.

**The model is pinned to `gpt-5.6-terra`.** Every number in the README comes
from it. It lives in exactly one constant, read from env with that default.
Switching models mid-project silently invalidates every earlier run — the stored
numbers stay in the SQLite store looking comparable when they are not. If the
model ever changes, every prior number is retired, not carried forward.

Do not use the bare `gpt-5.6` alias: it routes to `gpt-5.6-sol`, a different and
pricier model. Always the full id.

**`gpt-5.6-terra` API gotchas.** `temperature`, `top_p`, and `n` are fixed at 1
and `presence_penalty` / `frequency_penalty` at 0 — reasoning models reject any
other value. **There is no determinism knob**, which is why every number ships
with a measured noise band. Reasoning tokens bill as *output* tokens, so output
cost runs well above what the visible reply length suggests. Get SQL back with
native structured outputs (`response_format: { type: "json_schema", strict: true }`),
never by scraping a fenced code block.

**Generated SQL executes as the `queryproof_ro` role**, which has `SELECT` only.
A regex over generated SQL is a speed bump; the role is the wall. Never run
generated SQL as `postgres`. One path exists — `executeReadOnly` in
`src/execute-readonly.ts`; it refuses to open a pool as any other role. A
Postgres error comes back as a result with its `code`, never as a throw.

**Eval runs call OpenAI directly. Only the product path goes through Respan.**

The Respan gateway caches responses automatically, and an identical prompt
returns a cached reply. That silently destroys the noise floor: a cached repeat
run shows zero variance and looks perfectly stable, so ordinary run-to-run wobble
gets read as a real improvement. Respan's docs do not document a per-request
cache bypass, so the split is the fix rather than a flag.

Nothing is lost by it — the OpenAI SDK returns `usage` tokens on every response
and evalite stores them, so eval runs still capture cost. The product path keeps
the gateway, where caching, fallback, and traces are all wins.

```
eval runs    ->  api.openai.com          (no cache, honest variance)
product path ->  api.respan.ai/api/      (cache, fallback, tracing)
```

## Code style

- **Never use `any`.** Use the real type, `unknown` at boundaries, a union, or a
  generic. `catch (err: unknown)` and narrow.
- Prefer the simpler construct: a function over a class, an inline `if` over a
  dispatch table, three near-duplicate lines over a premature abstraction.
- Comment only what the code cannot say about itself — a non-obvious why, a
  gotcha, the origin of a magic value. Never restate the code.
- Obvious names over short ones.

## Rules

- **Adopt for plumbing, hand-write the domain logic.** Settled, per piece:

  | Piece | Choice |
  |---|---|
  | Run storage, run diffing, results UI | `evalite` |
  | Noise floor (repeat runs + variance) | `evalite`'s `trialCount` |
  | Tracing, cost, latency, fallback, caching — **product path only** | Respan gateway |
  | Row comparator, table recall, table selection, read-only path, gold-set handling, prompt construction | hand-written |
  | Respan's eval product | **not used** — it is the thing being learned from first principles |

  **Never** use an off-the-shelf scorer. Text-similarity and LLM-as-judge are
  both banned regardless of what a framework ships with.
- **Use Context7 for library docs** before writing against `evalite` or Next.js
  — they change faster than recalled API shapes. Respan's docs are at
  `respan.ai/docs`; fetch them rather than recalling the SDK shape.
- **Run `/test-guard` on every test file you write or change**, before presenting
  it. Not optional.
- **Run `npm run lint` and fix all errors before any commit.**
- **Never `git commit` or `git push` without explicit instruction in that turn.**
  "Feature complete" is not permission.
- `data/` and `gold/` are gitignored. The repo ships the script that regenerates
  them, not the data (BIRD Mini-Dev, CC BY-SA 4.0).
- Every eval run file records its full configuration — prompt version, model,
  effort, picker, limit, mode. A run that does not record its config is not
  evidence.
