# QueryProof

A natural language interface to a real Postgres database, plus an eval harness
that measures how often it is right. Ask a question in English, it selects
relevant tables, an LLM writes SQL, it validates and executes read-only, and on a
Postgres error it feeds the error back and retries. The harness scores every
answer by running the generated SQL and the gold SQL and comparing returned rows.

The project exists to produce measured accuracy numbers. The README's results
table is the deliverable; everything else serves it.

## Stack

- TypeScript, Node. **No Python, ever.**
- `pg` for Postgres, `tsx` to run TypeScript directly
- `node:test` (Node built-in) for tests — no test-runner dependency
- `@anthropic-ai/sdk`, model `claude-opus-5`
- Next.js for the demo frontend (phase 8, not built yet)

## Commands

```bash
npm run validate-gold          # executes all 500 gold queries -> gold/*.json
npm test                       # node:test
npm run lint                   # MUST pass before any commit
```

## Structure


## Environment

- `DATABASE_URL` — `postgresql://postgres:devpass@localhost:5433/bird`
- `ANTHROPIC_API_KEY`

Both live in `.env` (gitignored). Read `DATABASE_URL` from env — never hardcode a
connection string, and **never hardcode a LAN IP**.

## Hard constraints

These bite on tasks that look unrelated to them.

**Postgres port 5433 is shared.** A native Postgres also binds `127.0.0.1:5433`
and shadows the Docker container `queryproof-pg`. The user stops it manually
before running anything. If a connection fails with `database "bird" does not
exist`, the native instance is answering — that is not a config bug.

**All 75 tables are in `public`.** Eleven BIRD databases merged into one
namespace, zero name collisions. There is no per-database separation in Postgres;
the only `db_id` → tables mapping is `data/minidev/MINIDEV/dev_tables.json`.

**Table names are lowercase in Postgres; column names are not.** `examination`
has `"Examination Date"`, `"aCL IgG"`, `"ANA Pattern"`. `dev_tables.json` holds
BIRD's *original* mixed-case names (`Player_Attributes`, `postHistory`, …) which
do **not** match Postgres. So: build every prompt and query from
`information_schema`, and quote every identifier exactly as stored. That one rule
removes all the special cases — including `order`, which is both a table name and
a reserved keyword and must always be written `"order"`.

**Gold record ids are array position, zero padded** (`bird-0000`). `question_id`
in the source file is **not** unique — ids 137 and 138 each appear twice.
**Never renumber.**

**Grading is execution-based only. No LLM judges anything, ever.** A query is
correct iff running it returns the same rows as the gold query.

**The row comparator is deliberately minimal.** Positional tuples, row order
ignored, column names ignored, duplicates significant (multiset). No float
rounding, no null normalization, no type coercion. This is stricter than BIRD on
duplicate rows on purpose. Do not add normalization without a real failure that
demands it, and when adding one, measure how many points it moves and record the
number. See `PLAN.md` § Deferred risks.

**Gold records store no result fingerprint.** `validate-gold` records `rowCount`
and `columns` only. Value canonicalization lives in the row comparator and
nowhere else — do not add a second one, and never hash rows for comparison.

**Accuracy denominator is `|validated|`** — currently 498 (500 gold − 2
quarantined − 0 rejected). Read it from the file at runtime; a hardcoded
denominator produces a wrong percentage instead of an error.

**`claude-opus-5` API gotchas.** `temperature` / `top_p` / `top_k` return HTTP
400 — there is no determinism knob, which is why every number ships with a
measured noise band. Assistant prefill also returns 400; use structured outputs
(`output_config.format`) to get SQL back. Thinking is on by default and counts
against `max_tokens`.

**Generated SQL executes as the `queryproof_ro` role**, which has `SELECT` only.
A regex over generated SQL is a speed bump; the role is the wall. Never run
generated SQL as `postgres`.

## Code style

- **Never use `any`.** Use the real type, `unknown` at boundaries, a union, or a
  generic. `catch (err: unknown)` and narrow.
- Prefer the simpler construct: a function over a class, an inline `if` over a
  dispatch table, three near-duplicate lines over a premature abstraction.
- Comment only what the code cannot say about itself — a non-obvious why, a
  gotcha, the origin of a magic value. Never restate the code.
- Obvious names over short ones.

## Rules

- **Prefer an existing eval framework over hand-rolled harness plumbing.** Run
  storage, repeat runs, run-to-run diffing, results viewer, response caching, and
  token/cost capture are commodity — adopt (`evalite`, `promptfoo`; `Langfuse` for
  tracing) rather than build. Hand-write only the domain logic: the row
  comparator, the read-only execution path, gold-set handling, table selection,
  and prompt construction. **Never** use an off-the-shelf scorer — text-similarity
  and LLM-as-judge scorers are both banned regardless of what the framework ships
  with. See `PLAN.md` §2b.
- **Use Context7 for library docs** before writing against `evalite`, `promptfoo`,
  `Langfuse`, or Next.js — they change faster than recalled API shapes.
- **Run `/test-guard` on every test file you write or change**, before presenting
  it. Not optional.
- **Run `npm run lint` and fix all errors before any commit.**
- **Never `git commit` or `git push` without explicit instruction in that turn.**
  "Feature complete" is not permission.
- `data/` and `gold/` are gitignored. The repo ships the script that regenerates
  them, not the data (BIRD Mini-Dev, CC BY-SA 4.0).
- Every eval run file records its full configuration — prompt version, model,
  effort, picker, limit, mode. A run that does not record its config is not
  evidence.
